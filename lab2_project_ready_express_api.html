Lab 2: Project-Ready Express API (Backend & CRUD)

 

Who does this lab?

This lab is for both CSE3CWA and CSE5006 students. Everyone completes Lab 1 and Lab 2. 

This lab uses the project_ready_express_api project. It is a backend-only application built with Node.js and Express. It has no web page of its own; you talk to it with HTTP requests. The goal is to install and run it, then send real requests to perform CRUD (Create, Read, Update, Delete) and watch how a request travels through the backend layers: route → validation → controller → service (business rule) → repository (data) and back as a JSON response. You will not change any code.

Part 1: Software setup

If you completed Lab 1, you already have Node.js, npm and the downloaded code, so you can skip to Part 2. If not, do the short setup below first.

sudo apt install -y git

Part 2: Run the API server

Move into the project and start it with the helper script. The script copies the example settings file to .env the first time, installs packages, and starts the server.

cd project_ready_express_api
chmod +x run_ubuntu.sh
./run_ubuntu.sh

The server starts on port 4000. The terminal prints the health and projects URLs, and the demo API key. Leave this terminal running.

 

Where is the data stored?

This teaching API keeps its projects in an in-memory array (in the running Node.js process), seeded from src/data/projects.data.js. That means changes you make with Create / Update / Delete are real while the server runs, but everything resets to the seed data when you restart the server. This keeps the lab simple and repeatable. Lab 3 (Next.js) uses a real file as its store so you can see data persist on disk.

Part 3: Read data (the "R" in CRUD)

You can read from the API with your browser or with the terminal. Open a second terminal (Ctrl + Alt + T) so the server keeps running in the first one.

Step 3.1 — Health check in the browser

Open this address in your browser:

http://localhost:4000/api/health

You should see a JSON response with "ok": true and a status of healthy.

Step 3.2 — List and read projects with curl

curl is a command-line tool that sends an HTTP request to a server and prints the raw response. It is how developers talk to an API directly, without a browser or any frontend. It is normally pre-installed on Ubuntu; check it, and install it if missing:

curl --version
# if it is missing:
sudo apt install -y curl

Now read data from the API. Each command below sends a request and prints the JSON response:

# list all projects
curl http://localhost:4000/api/projects

# list with filtering, sorting and pagination
curl 'http://localhost:4000/api/projects?status=on_track&sortBy=progress&order=desc&page=1&limit=2'

# read one project by id
curl http://localhost:4000/api/projects/1

The list response wraps the data in a consistent shape: { "ok": true, "data": [ ... ], "meta": { page, limit, total, totalPages } }. This ok / data / meta shape is produced in src/utils.js and used by every successful response.

Step 3.3 — Make the output readable

Raw JSON is hard to read on one line. Pipe it through a JSON formatter. If you do not have one, install jq once:

sudo apt install -y jq
curl -s http://localhost:4000/api/projects | jq

Part 4: Create, Update and Delete (the "C", "U", "D")

Read routes are public. Write routes (create, update, delete) are protected and require the demo API key header x-api-key: week6-demo-key. This shows how authentication middleware guards write access.

Step 4.1 — Create a project (POST)
curl -X POST http://localhost:4000/api/projects \
  -H 'Content-Type: application/json' \
  -H 'x-api-key: week6-demo-key' \
  -d '{"name":"Workshop API extension","owner":"Student","status":"on_track","category":"frontend","priority":"low","progress":25}'

You get back 201 Created and the new project, including a new id. Run the list command again and confirm the new project is there.

 

Allowed field values (must match exactly)

status: planning, on_track, at_risk, complete. category: frontend, database, authentication, devops. priority: low, medium, high. progress: a whole number 0–100. A project at 100 must have status complete.

Step 4.2 — Update a project (PATCH)

Use the id you got from the create step (for example 5). Change just one field:

curl -X PATCH http://localhost:4000/api/projects/5 \
  -H 'Content-Type: application/json' \
  -H 'x-api-key: week6-demo-key' \
  -d '{"progress":60}'
Step 4.3 — Delete a project (DELETE)
curl -X DELETE http://localhost:4000/api/projects/5 \
  -H 'x-api-key: week6-demo-key'
Step 4.4 — See the guards in action (error responses)

Try these on purpose to see how the API rejects bad requests:

# missing API key -> 401 Unauthorized
curl -X POST http://localhost:4000/api/projects \
  -H 'Content-Type: application/json' \
  -d '{"name":"No key","owner":"X","status":"planning","category":"frontend","priority":"low","progress":0}'

# invalid data (limit too large) -> 400 Bad Request with details
curl 'http://localhost:4000/api/projects?limit=999'

# unknown id -> 404 Not Found
curl http://localhost:4000/api/projects/999

Notice every error also uses a consistent shape: { "ok": false, "error": { "message": ... } }, with a details list for validation problems.

Part 5: Test with a graphical client (Postman-style)

curl is fast, but a graphical API client makes requests easier to read and re-run. On Ubuntu you can install Postman with one command using snap:

sudo snap install postman

A free, lighter alternative that also installs through snap is Hoppscotch or the VS Code "REST Client" extension; any of them works. In Postman:

  • Create a new request, set the method to GET and the URL to http://localhost:4000/api/projects, then select Send. The JSON response appears, nicely formatted.
  • For a create, set the method to POST and the same /api/projects URL. Under Headers add Content-Type: application/json and x-api-key: week6-demo-key. Under Body choose raw → JSON and paste the same JSON object you used with curl. Select Send and read the 201 response.
  • Repeat for PATCH and DELETE using the id of the project you created.

This is exactly how professional developers talk to a backend while building it, before any frontend exists.

Part 6: Understand the request flow through the layers (no code changes)

The whole point of this project is that the backend is not one big file. Each responsibility lives in its own layer. Open the files in src/ with a native editor and match each one to a stage of the request. To read a file:

cat src/routes/projects.routes.js
less src/services/projects.service.js
nano src/repositories/projects.repository.js   # Ctrl+X to exit
vi src/schemas/projects.schema.js               # :q then Enter to exit

New to these editors? Official guides: nano at https://www.nano-editor.org/docs.php and vi/Vim at https://www.vim.org/docs.php. For reading only, cat and less need no editor knowledge.

Follow a POST /api/projects request through the layers, in order:

  1. Entry point — src/server.js starts the server on port 4000; src/app.js wires up security (helmet, cors), JSON parsing, logging, and the routes.
  2. Route — src/routes/projects.routes.js maps each HTTP method and path to its handler, and lists the middleware that runs first (auth, then validation):
projectsRouter.post("/", authRequired, validate({ body: projectCreateSchema }), controller.createProject);
  1. Authentication — src/middleware/authRequired.js checks the x-api-key header. Wrong key → 401, and the request stops here.
  2. Validation — src/middleware/validate.js with src/schemas/projects.schema.js checks the body against the rules (a Zod schema). Bad data → 400 with details.
  3. Controller — src/controllers/projects.controller.js reads the validated input and calls the service. It does not contain business rules itself.
  4. Service (business rule) — src/services/projects.service.js applies rules, such as: a project at 100% progress must have status complete.
if (input.progress === 100 && input.status !== "complete") {
  throw new AppError(400, "A project with 100% progress should have status 'complete'.");
}
  1. Repository (data) — src/repositories/projects.repository.js is the only layer that touches the data array: it filters, sorts, paginates, finds, pushes, updates and splices records.
  2. Response — the controller sends a consistent JSON response through helpers in src/utils.js; unknown routes and thrown errors are handled centrally in src/middleware/errorHandler.js.

So one create request travels: route → auth → validate → controller → service rule → repository (data changes) → JSON response. Read is the same path without auth and without a rule. This separation is why a real backend stays maintainable as it grows: each concern can be changed in one place.

Part 7: View the seed data and confirm a reset

The starting data lives in a file. View it directly:

cat src/data/projects.data.js

To prove the in-memory behaviour: create a new project (Step 4.1), confirm it appears in the list, then stop the server with Ctrl + C and start it again with ./run_ubuntu.sh. List the projects once more — your created project is gone and only the seed data remains. This is the difference between an in-memory store (this lab) and a persistent store (Lab 3).

How to stop the server

Ctrl + C

Completion checklist

  • The API runs and http://localhost:4000/api/health returns ok: true.
  • You read the project list (GET), created one (POST), updated it (PATCH) and deleted it (DELETE).
  • You saw a 401 (no key), a 400 (invalid data) and a 404 (unknown id).
  • You sent at least one request from a graphical client (Postman-style).
  • You can name the file for the route, the validation schema, the business rule (service) and the data access (repository).
  • You can explain why a created project disappears after a server restart.
