Who does this lab?

This lab is for CSE5006 students only. CSE3CWA students are not required to complete Lab 3. 

This lab uses the nextjs_project_portal project. Unlike the first two projects, this is a full-stack application: frontend and backend live in one Next.js application. You will install and run it, follow the data flow, view and edit its file-based data store, and then make small, guided code changes to add a new feature and change the appearance. Everything below has been tested to work step by step.

Part 1: What is Next.js, and why is it different?

React on its own (Lab 1) is only a frontend library: it renders components in the browser and needs a separate backend (Lab 2) for data. Next.js is a framework built on top of React that combines both sides into one organised project. With Next.js you get, in a single application:

  • Server Components — pages that run on the server and can read data directly before sending finished HTML to the browser. They are fast and do not ship their code to the client.
  • Client Components — interactive pieces that run in the browser (marked with "use client"), used for forms, buttons and anything with browser state.
  • Server Actions — functions marked "use server" that a form can call directly to submit data, with no separate API call to write by hand.
  • Route Handlers — real JSON API endpoints (app/api/.../route.js) living in the same project.
  • File-based routing — the folder structure under app/ defines the URLs. app/page.jsx is the home page; app/api/projects/route.js is the /api/projects endpoint.
  • Loading and error UI — app/loading.jsx and app/error.jsx are shown automatically during loading or on error.

The special idea to remember: in Next.js, the same project decides what runs on the server and what runs in the browser. This is why it is called a full-stack React framework.

Part 3: Run the Next.js project

cd nextjs_project_portal
chmod +x run_ubuntu.sh
./run_ubuntu.sh

The first run installs packages, which can take a minute. When ready, open: 

http://localhost:3000

You will see a hero header, a summary panel, three status metrics, a "Create a project" form on the left, and a server-rendered list of project cards on the right.

Part 4: Use the app and watch the full-stack data flow

Use the Create a project form: enter a title and owner, choose a status and priority, then select Create project. The new project appears immediately in the list on the right, and the metric counts update. Notice you did not reload the page yourself.

Here is what happened across the stack:

  1. The form is a Client Component (components/ProjectForm.jsx, marked "use client"), so it can manage its own submitting state.
  2. On submit, it calls a Server Action (app/actions.js, marked "use server") directly — no fetch call is written by hand.
  3. The Server Action calls createProject in lib/projects.js, which validates the input and writes the new project to the data file on disk.
  4. The action calls revalidatePath("/"), which tells Next.js to re-render the home page.
  5. The home page (app/page.jsx) is a Server Component; it re-reads the data file and sends fresh HTML, so the new card appears.

This is the whole point of the framework: a browser action triggered a server function that changed stored data and re-rendered the page, all in one project.

Part 5: Test the built-in API (Route Handler)

The same project also exposes a JSON API. You will test it with curl, a command-line tool that sends an HTTP request and prints the raw response — the standard way developers talk to an API directly. It is normally pre-installed on Ubuntu; check it and install it if missing: 

curl --version
# if it is missing:
sudo apt install -y curl

You can also use a graphical client such as Postman (see Lab 2 for installing it with sudo snap install postman). Open a second terminal so the dev server keeps running, then test the API:

# read all projects as JSON
curl http://localhost:3000/api/projects

# create a project through the API
curl -X POST http://localhost:3000/api/projects \
  -H 'Content-Type: application/json' \
  -d '{"title":"Accessibility review","owner":"Mina","status":"planned","priority":"high"}'

# try invalid data to see the validation message (title too short)
curl -X POST http://localhost:3000/api/projects \
  -H 'Content-Type: application/json' \
  -d '{"title":"ab","owner":"X"}'

The valid create returns 201 and the new project; the invalid one returns a clear error message. Refresh http://localhost:3000 in the browser and the project you created through the API also appears in the list — the form and the API share the same data file.

 

Allowed field values

status: planned, in_progress, complete. priority: low, medium, high. title: at least 3 characters. owner: at least 2 characters.

Part 6: View the file-based data store directly

Unlike Lab 2 (in-memory), this project stores data in a real file: data/projects.json. You can read it with native Ubuntu tools:

cat data/projects.json

Create a project (via the form or the API), then run cat again: the new record is now written into this file. This is your "database table" in file form.

Insert a record directly into the store, then refresh the UI

You can add data straight to the file and the running app will show it, because the home page re-reads the file on every visit. Open the file in a native editor:

nano data/projects.json

The file is a JSON array. Add a new object as the first item, right after the opening [, and make sure there is a comma after it. Use a recent date so it sorts to the top:

[
  {
    "id": "manual-001",
    "title": "Inserted directly into the file",
    "owner": "Admin",
    "status": "in_progress",
    "priority": "high",
    "createdAt": "2026-12-31T09:00:00.000Z"
  },
  ... keep the existing projects here ...
]

Save the file (in nano: Ctrl + O, Enter, then Ctrl + X). Switch to the browser and refresh http://localhost:3000 with F5. Your manually inserted project now appears at the top of the list, because the Server Component re-read the file. This shows clearly how stored data flows back into the rendered page on each request. (You can remove that entry later to restore the original data.)

 

Why a refresh is enough here

The home page sets export const dynamic = "force-dynamic", so Next.js does not cache it; every visit re-reads data/projects.json. A real application would use a database instead of a JSON file, but the flow — store changes, then the page shows them — is the same idea.

Part 7: Read the code with native tools (no changes yet)

Open these files and match each to its role in the framework:

cat app/page.jsx              # Server Component home page
cat components/ProjectForm.jsx # "use client" interactive form
cat app/actions.js             # "use server" Server Action
cat app/api/projects/route.js  # Route Handler (JSON API)
cat lib/projects.js            # data read/write + validation
cat components/ProjectCard.jsx # how each project is displayed

To edit (in Part 8) you can use nano (beginner-friendly) or vi. Official guides: nano at https://www.nano-editor.org/docs.php and vi/Vim at https://www.vim.org/docs.php. In nano, save with Ctrl + O then Enter, and exit with Ctrl + X.

  • app/page.jsx begins with no "use client", so it is a Server Component. It calls getProjects() directly — server code reading data before rendering.
  • components/ProjectForm.jsx starts with "use client" because it uses browser interactivity (useActionState).
  • app/actions.js starts with "use server"; its createProjectAction is the function the form submits to.
  • lib/projects.js is the only place that reads and writes data/projects.json and enforces the validation rules.

Also look in the browser developer tools (F12): on the Network tab, refresh and notice the home page arrives as ready-made HTML from the server (Server Component), while /api/projects returns JSON when you call it. This is the server/client split in action.

Part 8: Add a new feature — a project "description" (guided code change)

Now you will add a description field that flows through the whole stack: form → Server Action → data file → card. Make all five edits below, then test. Each edit is small. Keep the dev server running; Next.js reloads automatically.

Edit 1 — accept and store it. In lib/projects.js, inside createProject, read the description and include it in the saved object. Find the line that reads priority and add a description line after it:

const priority = cleanText(input.priority || "medium");
const description = cleanText(input.description);

Then, in the same function, add description to the object that is pushed (after the priority line):

    status,
    priority,
    description,
    createdAt: new Date().toISOString()

Edit 2 — forward it from the Server Action. In app/actions.js, add description to the object passed to createProject (after the priority line):

      status: formData.get("status"),
      priority: formData.get("priority"),
      description: formData.get("description")

Edit 3 — add the input to the form. In components/ProjectForm.jsx, add a description field after the Owner label:

      <label>
        Description
        <textarea name="description" placeholder="Short summary of the project" rows={3} />
      </label>

Edit 4 — show it on each card. In components/ProjectCard.jsx, add a line that shows the description when present, just after the Owner paragraph:

        <h3>{project.title}</h3>
        <p>Owner: {project.owner}</p>
        {project.description ? <p className="description">{project.description}</p> : null}

Edit 5 — style the new text. In app/styles.css, add this rule at the end of the file:

.description {
  color: var(--muted);
  font-size: 0.92rem;
  margin-top: 0.35rem;
}

Test it. In the browser, create a project and type something in the new Description box. The new card shows your description, and cat data/projects.json shows a description field saved in the file. You added one field across the form, the server action, the data layer and the display — the full stack.

Part 9: Upgrade the appearance (guided style change)

The whole colour scheme is controlled by CSS variables at the top of app/styles.css, inside the :root block. Changing a few variables restyles the entire app at once. Open the file:

nano app/styles.css

Find these three lines near the top and change the colour values from the teal/amber theme to a purple/pink theme:

/* change FROM */
--brand: #0f766e;
--brand-dark: #115e59;
--accent: #b45309;

/* change TO */
--brand: #6d28d9;
--brand-dark: #5b21b6;
--accent: #db2777;

Save the file. The browser updates instantly: the hero banner, headings, buttons, focused inputs and highlights all switch to the new colours, because every component reads these variables. This shows how a well-structured stylesheet lets you re-theme an app by editing a few values in one place, without touching any component. Experiment with your own colours, then restore the originals if you wish.

How to stop the server

Ctrl + C

Restart with ./run_ubuntu.sh from the nextjs_project_portal folder. For a production build instead of the dev server, you can run npm run build then npm run start.
